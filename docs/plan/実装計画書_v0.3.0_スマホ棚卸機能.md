## 1. 目的

- 事務所 PC のネットワーク外にある各クライアント現場へ Android スマートフォンを持ち出し、ブラウザ上のボタン操作(ポチポチ入力)で月次棚卸を完結させ、帰社後に事務所 PC へ安全に一括反映できるようにする。
- アプリケーションのオフライン原則(ブラウザ起動以外の外部通信・ポート待受を行わない)を維持するため、対象クライアントの品目データと操作 UI(CSS/JavaScript)を単一ファイルに内包した**自己完結型 HTML シート**を出力し、帰社後は**結果テキスト(`IMM1:...:END`)のコピー＆貼り付け**または**結果ファイル(`.json`)の読込**の 2 経路で取り込めるようにする。
- 棚卸シート出力中(棚卸手続き中)の在庫変動や品目構成の食い違いによる不整合を確実に防ぐため、DB スキーマを `v5`(`active_stocktakes` テーブル追加)へ引き上げ、**棚卸手続き中の対象クライアントに関わる在庫操作・品目追加/編集/廃止・対象クライアント自身の無効化/削除を全面禁止する厳格ロック(方式①)**を導入する。
- 出発前の「棚卸シート出力・ロック管理」と帰社後の「結果取り込み・差分プレビュー・一括確定」を 1 つの専用ダイアログ(`MobileStocktakeDialog`)およびメイン画面上部の通知バナーに集約し、操作者が迷わない導線を提供する。
- 上記の機能追加に伴い、アプリケーションの版数を `0.2.0` から `0.3.0` へ、DB スキーマ版数を `4` から `5` へ引き上げ、確定した仕様を開発計画書(正本)へ統合する。

## 2. 要件

### 2.1 満たすべき仕様

- 開発計画書 3.1(層構成と依存方向)、3.3(業務例外)、3.4(DB 接続・トランザクション・日時表現)、4.2〜4.4(スキーマ・マイグレーション)、5.1〜5.4(品目・在庫操作・FIFO 引当・取り消し・マスタ管理)、6.1〜6.4(画面設計・表示要件)、7.2(バックアップ・復元)、7.4(セキュリティ)、8 章(テスト方針)、9.2(パッケージング)に従う。
- `core/` と `db/` は `PySide6` を絶対に import しない。UI は `sqlite3` や `inventory_manager_mini.db` を直接扱わず、Service(`InventoryService`・`MasterService`・`ReportService`・`SettingsService`・`BackupService`)のみを経由する。
- `core/models.py` および `core/errors.py` は `db/`・Service・UI に依存させない。
- 現在時刻の取得・変換は `core/timeutil.py` に集約し、それ以外で `datetime.now()` や SQLite の `'localtime'` を使用しない。
- SQL はすべてプレースホルダでパラメータ化し、f-string 等で値を埋め込まない。
- 最小解像度 1366×768 かつ文字サイズ 100%・150% のいずれでも、新設する `MobileStocktakeDialog` および棚卸中バナー表示時の `MainWindow` が対象画面の `availableGeometry()` 内に収まり、すべての操作欄・ボタンに到達可能であること。
- 次のコマンドがローカル(Windows)と CI(Windows/Linux)で成功すること。
  - `uv sync --locked`
  - `uv run ruff check` / `uv run ruff format --check`
  - `uv run pyright`(`core/`・`db/` は strict、`ui/` は standard でエラー 0 件)
  - `uv run pytest --cov`(Linux は `QT_QPA_PLATFORM=offscreen`)
  - `uv run coverage report --include="src/inventory_manager_mini/core/*,src/inventory_manager_mini/db/*" --fail-under=90`
  - `uv run python scripts/check_release_version.py --version 0.3.0`
- テストで実データの保存先(`%APPDATA%` 等)を使用しない。ファイル選択ダイアログ・メッセージボックス・クリップボード操作はテストで検証可能にする。
- ブラウザ自動テストには開発依存の `playwright` と Chromium を使用する。`uv sync --locked` 後、Windows は `uv run playwright install chromium`、Linux は `uv run playwright install --with-deps chromium` で準備する。CI(`ci.yml`)およびリリース検証(`release.yml`)、README の検査手順、`SOURCE_CODE.txt`、開発計画書(正本)にも本準備手順を反映する。生成 HTML をローカルファイルとして開き、HTTP サーバーを起動せず検証する。依存・ブラウザの取得は開発時だけに限定し、アプリおよび出力 HTML の外部通信禁止は維持する。
- DB 改修(B 以降)に着手する前に A0 の Android 最小実証を完了し、対応端末・開き方・途中保存と再開の条件を確定する。

### 2.2 既存実装の状況(調査結果)

| 項目 | 状況 |
| --- | --- |
| スキーマ・マイグレーション | 現行は `SCHEMA_VERSION = 4`、`MIN_SUPPORTED_SCHEMA_VERSION = 1`。`db/schema.sql` が最新版(v4)であり、v3 は `db/schema_v3.sql` として固定保存されている。`scripts/check_bundle.py` と `tests/test_check_bundle.py` が `db/schema.sql` と `db/schema_v3.sql` の同梱を検査している |
| 個別棚卸(`InventoryService.stocktake`) | 単一品目に対し `actual_quantity`(`0〜MAX_STOCK_QUANTITY`)を受け取り、`delta = actual - item.quantity` で `Reason.ADJUST` 履歴を記録する。`delta == 0` でも記録し、`delta > 0` は `item.reference_price` をロット単価とし、`delta < 0` は `plan_fifo_allocations` で FIFO 引当を行う |
| 集計管理テーブル(`total_aggregates`) | `Reason.ADJUST` は入庫数・出庫数・廃棄数・支出額・廃棄額のいずれにも計上しないため(`_aggregate_deltas` が空辞書を返す)、一括棚卸でも `total_aggregates` の値は変化しない(減少時の `stock_allocations` のみ追加される) |
| マスタ使用中判定(`MasterRepository`) | `client_in_use` は `items` と `stock_movements`、`staff_in_use` は `stock_movements` の参照有無を検査している |
| 依存ルール検査(`tests/test_dependency_rules.py`) | `core/`・`db/` の `PySide6` 非依存、`db/` から Service/UI への import 禁止、`core/models.py`・`core/errors.py` の独立性、`core/timeutil.py` 以外での `datetime.now` / `'localtime'` 禁止を AST で自動検査している |
| 記録処理(`InventoryService._record_movement`) | 呼び出しごとに `utc_now_str(self.clock())` で記録時刻を取得し、品目ごとの最新履歴時刻と比較する。1 回の操作で複数品目を記録する処理(一括棚卸)では、記録時刻を呼び出し側から指定できない |
| ファイル出力 | `core/reports.py` の `_write_csv` が一時ファイルへ書き込み `os.replace` で置き換える方式を採用している |
| 整合性検査の版数分岐 | `db/integrity.py` は `schema_version >= 4` で FIFO 方式に切り替え、`BackupService.inspect_database` も `version >= 3`・`version >= 4` で分岐するため、v5 にも既存の検査がそのまま適用される |
| 復元(`PreparedRestore`・`MainWindow._restore_backup`) | 復元確認ダイアログは復元元の版数・品目数・履歴数・最終履歴日時を表示する。`PreparedRestore` に棚卸手続きの情報はない |

### 2.3 決定事項

| 項目 | 決定 |
| --- | --- |
| アプリ版数・スキーマ版数 | アプリ版数を `0.3.0` に引き上げる(`pyproject.toml`・`uv.lock`・`README.md`)。DB スキーマ版数を `SCHEMA_VERSION = 5` に引き上げ、現行の v4 DDL を `db/schema_v4.sql` として固定保存する(`scripts/check_bundle.py` の必須ファイルにも追加)。v5 の差分 DDL(`_MIGRATION_V5_SQL`)は `schema.sql` の `active_stocktakes` 定義と同一内容とし、正規化後の一致をテストで検証する。v0.3.0 の DB・バックアップは v0.2.0 以前のアプリでは開けない(`SchemaTooNewError`)ため、README に明記する |
| 棚卸管理テーブル(`active_stocktakes`) | `client_id INTEGER PRIMARY KEY REFERENCES clients(id)`、`session_id TEXT NOT NULL UNIQUE CHECK (length(session_id) = 32 AND session_id NOT GLOB '*[^0-9a-f]*')`、`staff_id INTEGER NOT NULL REFERENCES staff(id)`(シートを作成した担当者の記録であり、担当者マスタのロック対象ではない)、`started_at TEXT NOT NULL DEFAULT (datetime('now'))` を持つテーブルを追加する。`session_id` は `secrets.token_hex(16)` で生成する。主キーを `client_id` とすることで、クライアント単位で独立して複数同時に棚卸手続きを進められる |
| 開始条件と再出力 | 有効なクライアントかつ有効な担当者を選択して開始する。対象クライアントの有効品目(`is_active = 1`)が 0 件の場合は `ValidationError("対象クライアントに有効な品目がありません")` として開始不可とする。すでに棚卸手続き中のクライアントに対して再度シート出力を実行した場合は、新しい `session_id` と開始時刻で `active_stocktakes` を更新(再発行)し、旧シートの結果は無効なセッションとして拒否する。ロックの登録(開始)はシート出力と同一トランザクションで行う。書き込み・COMMIT に失敗した場合、新規開始ではロックを残さず、再出力では旧セッションを維持する |
| HTML 出力ファイルの保全 | 各セッションは別の新規パスへ保存し、既存ファイルへの上書きを禁止する。Service は排他的な新規作成(`path.open("x", encoding="utf-8")`)を使い、既存パスは `FileOutputError` で拒否する。失敗時に削除してよいのは今回の呼び出しが新規作成したファイルだけとし、旧シートや他のファイルを変更・削除しない。CSV の上書き方式(`os.replace`)は流用しない |
| 厳格ロックの禁止範囲(`StocktakeInProgressError`) | 対象クライアントが `active_stocktakes` に存在する間、以下の操作をすべて `StocktakeInProgressError` で拒否する。<br>1. 当該クライアントへの新規品目登録(`create_item`)<br>2. 当該クライアントに属する品目の属性編集(`update_item`)、および別クライアントの品目を当該クライアントへ変更する編集<br>3. 当該クライアントに属する品目の廃止(`deactivate_item`)・再有効化(`reactivate_item`)<br>4. 当該クライアントに属する品目の全在庫操作(`receive`、`issue`、`return_to_supplier`、`dispose`、`stocktake`)<br>5. 当該クライアントに属する品目の履歴取り消し(`reverse`、および `reversal_block_reason` での理由返却)。判定は取り消し元履歴の記録時点のクライアントではなく、品目の現在のクライアント(`items.client_id`)で行う<br>6. 当該クライアント自身の無効化(`deactivate_client`)・物理削除(`delete_client`)、およびシート作成担当者(`active_stocktakes.staff_id`)の物理削除(`delete_staff`)。担当者の無効化は禁止しない(確定時に有効な担当者を選び直すため) |
| ロック検査の実装方針 | マスタの使用中判定(`MasterRepository.*_in_use` と `MasterService.can_delete_*` の既存の意味)は変更しない。`MasterService` に専用の棚卸ロック検査を設け、`_set_active`(無効化時のみ)と `_delete` の先頭で `StocktakeInProgressError` を送出する。`MasterService.stocktake_lock_reason(kind, entity_id)` が理由文字列(なければ `None`)を返し、`MasterDialog` が無効化・削除ボタンの活性制御とツールチップに使う |
| ロック中に許可する操作 | 別クライアントの品目に対する全操作、当該クライアント名・担当者名の名称変更、シート作成担当者の無効化、全クライアントの閲覧・検索・CSV 出力・印刷・ダッシュボード集計・バックアップは通常どおり許可する |
| ロック解除(棚卸中止) | `InventoryService.cancel_mobile_stocktake(client_id)` により、いつでも `active_stocktakes` から対象クライアントのレコードを削除してロックを解除できる |
| スマホ側の確認状態と入力制約 | 初期状態は全品目が未確認。「帳簿通りで OK」は帳簿数量を設定して確認済みにし、差異がある場合は数量入力後に「この実数で確認」で確認済みにする。「確認解除」を用意し、数量またはメモを変更した場合も未確認に戻す(入力操作だけでは確認済みにしない)。実数は `0〜MAX_STOCK_QUANTITY` の整数、メモは前後空白除去後に最大 500 文字とし、Python と JavaScript とも Unicode コードポイント数で数える。空欄・小数・範囲外数量・長すぎるメモは明示的にエラーとし、暗黙の丸め・切り詰めはしない。**全品目が確認済みかつ全入力が正常な場合だけ、結果のコピー・ファイル保存・テキスト表示を許可する**。PC 側も全有効品目の網羅と入力制約を再検証する |
| HTML シートの機能・UX | ・外部 CDN やネットワーク通信を一切使わない単一 `.html` ファイル(インライン CSS/JS + JSON データ)として生成する。<br>・Android の簡易 HTML ビューア(JS 無効環境)で開かれた際に、「右上のメニューから Chrome で開いてください」と大きく表示する `<noscript>` ガードを設ける。<br>・上部固定ヘッダに進捗バー(`確認済 X / Y 件`)、状態タブ(`未確認` / `確認済` / `差異あり` / `すべて`)、保管場所フィルタ、キーワード検索(管理番号・品名・メーカー型番)を設ける。<br>・品目カードには帳簿通りのワンタップ確認、`-10` / `-1` / `実数直接入力` / `+1` / `+10`、メモ、「この実数で確認」「確認解除」を設ける。<br>・操作ごとにブラウザの `localStorage`(キー: `imm_stocktake_<session_id>`)へ自動保存し、復元時もセッション・品目・数量・メモ・確認状態を検証する。ローカルファイルでの永続化は環境依存のため、再開対応は A0 で実証した端末・開き方・同一ファイルの条件に限定する。<br>・保存領域の読み書きに失敗したときは「途中保存できません。画面を閉じないでください」と警告する。<br>・結果テキストの検査値には `crypto.subtle` を使わず、安全でないコンテキストでも動作する CRC-32 を自前で実装する。 |
| 結果出力の代替経路 | 全件確認・入力正常後は、コピーやファイル保存の成否に関係なく「結果テキストを表示」を利用可能にする。コピー失敗時や保存処理で例外が発生した場合は、自動で結果テキストを全選択状態の `<textarea>` に表示し「長押しでコピーしてください」と案内する。`<a download>` では実際の保存成功・拒否・キャンセルを確実に判定できないため、保存完了を断定する表示や失敗検出だけに依存した代替経路は設けない |
| 引用返信の複数結果 | `IMM1:` 結果ブロックが複数含まれる場合は、空白・改行・行頭の引用符除去後の文字列が完全一致する重複だけを 1 件として扱う。異なるブロックが複数ある場合は、同一セッションでも先頭・末尾・有効なものを自動選択せず、`ValidationError("複数の棚卸結果が含まれています。取り込む結果を1件だけ貼り付けてください")` で拒否する |
| プレビューと確定入力の一致 | 結果テキストの変更、別ファイル・クリップボードの読込開始、読込・解析・プレビューの失敗時には、前回のプレビューと確定用入力を破棄して確定ボタンを無効化する。正常プレビューに使用した入力文字列を保持し、確定時は現在の入力欄ではなく保持した文字列だけを Service へ渡す。変更後は再プレビューを必須とし、Service 側の再検証も維持する |
| スマホから PC への戻し方 | 以下の 2 通りを両方提供する。<br>1. **結果テキスト(`IMM1:<Base64>.<検査値>:END`)**: JSON ペイロードを UTF-8 → 標準 Base64 エンコードし、Base64 文字列の CRC-32(小文字 16 進 8 桁)を検査値として `IMM1:` と `:END` で囲んだ文字列をクリップボードへコピーする(メール本文等に貼り付けて送信可能)。PC 側は `IMM1:` から `:END` までを抽出し、空白・改行・行頭の引用符 `>` を除去してから検査値を照合する。メーラーの折り返しや引用付き返信、前後の本文が含まれていても取り込めるようにし、途中で欠けたテキストは検査値の不一致で拒否する。<br>2. **結果ファイル(`.json`)**: 同じ JSON ペイロードを `棚卸結果_<クライアント名>_<日時>.json` としてスマホに保存し、PC 側のファイル選択ダイアログで読み込む。 |
| PC 側の取り込み・一括確定 | ・`preview_mobile_stocktake(raw_text)` は、結果データの `session_id` から DB の `active_stocktakes` の記録を特定し(結果データの `client_id` は DB の記録との一致の照合にのみ使う。スマホ側のデータを信用しない)、フォーマット・全有効品目の網羅・数量上限(`0〜MAX_STOCK_QUANTITY`)を検証し、品目ごとの帳簿数量・棚卸実数・差分・メモおよび集計サマリ(総件数・変動なし・増加・減少)を返す。<br>・`complete_mobile_stocktake(raw_text, staff_id)` の確定担当者 `staff_id` は省略不可とし、UI で有効な担当者を選択させる(初期値はシート作成担当者。結果データに担当者は含めない)。単一の `transaction(self.conn)` 内で再検証し、記録時刻を 1 回だけ取得して全対象品目の時計巻き戻り検査を記録開始前に済ませた上で、品目順(`code, id` 昇順)に `Reason.ADJUST` の履歴 INSERT(差分 0 もすべて記録。`delta > 0` は参考価格を単価とし、`delta < 0` は `plan_fifo_allocations` で FIFO 引当を記録)・`items.quantity` 更新を行い(全履歴は同一の `moved_at`。各履歴の `note` には結果データの品目メモを保存し、メモなしは NULL)、最後に `active_stocktakes` から当該クライアントを削除する。途中で 1 件でも失敗した場合は全件ロールバックする。 |
| PC 側の導線と画面構成 | ・「在庫」メニューおよびツールバーに「スマホ棚卸…」(`mobile_stocktake_action`、常時活性)を追加する。<br>・棚卸手続き中のクライアントが 1 件以上ある場合、`MainWindow` の一覧テーブル上部に通知バナーと「スマホ棚卸を開く…」ボタンを表示する。1 件のときは `📱 スマホ棚卸手続き中: <クライアント名> (開始: ... / 担当: ...)`、複数件のときは `📱 スマホ棚卸手続き中: A社(10/17 09:30)、B社 ほか N 件`(開始が古い順に最大 2 件)と表示し、詳細は `MobileStocktakeDialog` で確認する。<br>・`MainWindow` で棚卸手続き中クライアントの品目を 1 件選択している場合、編集・廃止/再有効化・在庫操作アクションを不活性化し、ツールチップに「このクライアントはスマホ棚卸手続き中のため操作できません」を表示する(非ロック品目または未選択に切り替わった際はツールチップを元に戻す)。<br>・`StockMoveDialog` はロック中クライアントの品目を選択した時点、および `_validate()` 内で理由を表示して OK を不活性にする。<br>・`ItemDialog` はロック中クライアントに「(棚卸中)」を付け、選択時(編集時は現在のクライアントがロック中の場合を含む)に OK を不活性にして理由を表示する。<br>・`MasterDialog` は棚卸中のクライアント・シート作成担当者について、削除ボタン(クライアントは無効化ボタンも)を不活性にし、専用の理由をツールチップに表示する。<br>・棚卸の中止(ロック解除)は確認ダイアログ(既定ボタンは「いいえ」)を経て実行する。 |
| バックアップ・復元時の扱い | `active_stocktakes` は DB に含まれるため、バックアップ・復元の対象とする。復元後の棚卸手続きの状態は復元元のとおりになる(v1〜v4 の復元元は棚卸手続きなしとして移行する)。復元の確認ダイアログには、現在の DB で棚卸手続き中のクライアント名と復元元で棚卸手続き中のクライアント名を表示し、「復元すると棚卸手続きの状態が置き換わり、持ち出し中のシートの結果は取り込めなくなる場合がある」旨を注意表示する。`PreparedRestore` に復元元の棚卸中クライアント名(`stocktake_client_names: tuple[str, ...]`、既定は空)を追加する |
