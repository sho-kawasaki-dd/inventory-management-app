- ステータス: 計画中
- 作業ブランチ: `feature/v0.3.1-plan`(計画書作成)→ `feature/v0.3.1-item-code`(実装・正本統合)
- 基盤とする文書: [ローカル在庫管理アプリ開発計画書](ローカル在庫管理アプリ開発計画書.md)(1.3・1.6・3.1・3.4・4.2・4.3・5.1・5.4・5.8・6.3・8 章)

---

## 1. 目的

- メインウィンドウの在庫一覧に「用途」列を表示し、在庫表印刷・CSV 出力では確認できていた用途を一覧でも確認できるようにする。
- 既存品目のカテゴリを変更したとき、管理番号が旧カテゴリの接頭辞のまま残り、カテゴリと管理番号が食い違う状態を解消する。変更後のカテゴリの接頭辞で管理番号を自動的に再採番する。
- 上記の改修に伴い、アプリの版数を `0.3.0` から `0.3.1` へ引き上げ、確定した仕様を開発計画書(正本)へ統合する。

## 2. 要件

### 2.1 満たすべき仕様

- 開発計画書 3.1(層構成と依存方向)、3.4(DB 接続・トランザクション)、4.2・4.3(スキーマ・カラム運用ルール)、5.1(管理番号・採番)、5.4(マスタ)、5.8(CSV)、6.3(画面詳細)、8 章(テスト方針)に従う。
- `core/` と `db/` は `PySide6` を import しない。UI は Service のみを経由し、Repository や SQL を直接扱わない。
- 再採番と品目の更新は、`InventoryService.update_item` の 1 トランザクション(`BEGIN IMMEDIATE`〜`COMMIT`)で行い、途中で失敗した場合は `categories.next_seq` の加算を含めてすべて元に戻す。
- SQL はすべてプレースホルダでパラメータ化する。
- 最小解像度 1366×768 かつ文字サイズ 100%・150% のいずれでも、改修後の `ItemDialog`(確認ダイアログを含む)が画面内に収まり、すべての操作に到達可能であること。
- 次のコマンドがローカル(Windows)と CI(Windows/Linux)で成功すること。
  - `uv sync --locked`
  - `uv run ruff check` / `uv run ruff format --check`
  - `uv run pyright`(`core/`・`db/` は strict、`ui/` は standard でエラー 0 件)
  - `uv run pytest --cov`(Linux は `QT_QPA_PLATFORM=offscreen`)
  - `uv run coverage report --include="src/inventory_manager_mini/core/*,src/inventory_manager_mini/db/*" --fail-under=90`
  - `uv run python scripts/check_release_version.py --version 0.3.1`
- テストで実データの保存先(`%APPDATA%` 等)を使用しない。確認ダイアログ(`QMessageBox.question`)はテストで差し替える。

### 2.2 既存実装の状況(調査結果)

| 項目 | 状況 |
| --- | --- |
| 一覧の列 | `ItemTableModel._COLUMNS` は 15 列(管理番号・品名・メーカー型番・クライアント・発注主体・カテゴリ・保管場所・数量・単位・閾値・推奨発注数・参考価格・仕入先・最終購入日・状態)。`ItemRow` は `application` を持つが一覧には出ていない。開発計画書 6.3 は「用途は一覧に表示しない」と明記している |
| 列添字の直書き | `ItemTableModel._NUMERIC_COLUMNS = {7, 9, 10, 11}`、`_display_value` の `column == 11`(参考価格)・`13`(最終購入日)・`14`(状態)が添字を直書きしている。`tests/test_item_table_model.py`(列数 15、添字 0〜14)と `tests/test_performance.py` のソート検証(数量 = 列 7)も添字に依存する。列の幅・順序・表示/非表示の保存機能はない |
| 用途の他の出力 | CSV(在庫一覧、`ReportService.export_items_csv`)と在庫表印刷(`INVENTORY_SHEET_COLUMNS`)には用途がすでに含まれ、変更不要 |
| 管理番号の採番 | `ItemRepository.allocate_code(category_id)` が `UPDATE categories SET next_seq = next_seq + 1 ... RETURNING code_prefix, next_seq - 1` で連番を確保し、`{接頭辞}-{連番:04d}` を返す。`items.code` は `UNIQUE NOT NULL`。`InventoryService.create_item` だけが呼び出す |
| 品目の更新 | `InventoryService.update_item` はカテゴリを変更できるが `code` は更新しない。`ItemRepository.update` の `UPDATE` 文にも `code` は含まれない。現行仕様は「管理番号は登録後不変。カテゴリ変更でも再採番しない」(開発計画書 1.3・4.2 のスキーマ注記・4.3・5.1) |
| `next_seq` の保持 | カテゴリ変更後も旧カテゴリの `next_seq` は保持する(接頭辞変更・カテゴリ削除の禁止、番号の再利用防止。開発計画書 5.4)。この方針は維持する |
| 既存テストの前提 | `tests/test_inventory_service.py::test_category_code_sequence_is_not_reused_after_item_moves` は、品目をカテゴリ移動しても管理番号が変わらないことを前提にしている(新仕様で書き換えが必要)。`tests/test_reports.py` の `update_item`(L84・L1108 付近)、`tests/test_repositories.py` の `ItemUpdate`(L208・L1077 付近)はカテゴリ変更を伴う場合があり、管理番号・並び順の期待値に影響しないか確認が必要 |
| 棚卸との関係 | スマホ棚卸の手続き中は、対象クライアントの品目の編集を Service が拒否する(`_require_client_not_in_stocktake`)。そのため棚卸シートに出力済みの管理番号と食い違う再採番は起こらない |
| 版数定義 | `pyproject.toml` の `version = "0.3.0"` を正本とし、`__init__.py` は `importlib.metadata.version` で動的に取得する。`uv.lock` と `README.md`(インストーラー・ビルド例)に `0.3.0` が記載されている。DB スキーマの変更はなく、`SCHEMA_VERSION = 5` は維持する |

### 2.3 決定事項

| 項目 | 決定 |
| --- | --- |
| 用途列の位置 | メーカー型番の直後(添字 3)に追加する。在庫表印刷の列順(管理番号・品名・メーカー型番・用途…)に合わせる。一覧は 16 列になる |
| 用途列の仕様 | ヘッダーは「用途」。値は `ItemRow.application` をそのまま表示し、`None` は空欄、左寄せ(数値列に含めない)。ソートは既存の `ItemSortProxyModel` の文字列ソートに従い、`None` は末尾に置く。低在庫の着色・廃止のグレー表示は既存の行単位の処理に従う |
| 再採番の契機 | `update_item` で `current.category_id != value.category_id` のときだけ再採番する。カテゴリが同じなら管理番号は不変とする |
| 採番の基準 | 変更後のカテゴリの `next_seq`(登録時と同じ `allocate_code`)を使う。過去に発番した最大値+1 であり、他カテゴリへ移った品目の旧番号を再利用しない。既存の「番号を再利用しない」仕様と整合する。空き番号は埋めない |
| 旧カテゴリの `next_seq` | 変更しない(保持)。旧カテゴリの接頭辞・削除可否の制約も従来どおり |
| 元のカテゴリへ戻した場合 | 元のカテゴリの `next_seq` で新しい番号を採番する(以前の番号には戻らない) |
| 旧管理番号の記録 | 記録しない。履歴テーブル・備考への退避も行わない。印刷済みの棚ラベルは再印刷が必要となるため、確認ダイアログで周知する。スキーマ変更・マイグレーションは行わない |
| 画面での通知 | `ItemDialog`(編集時)の保存時に、選択カテゴリが開いた時点(`self.item.category_id`)から変更されていれば確認ダイアログ(`QMessageBox.question`、`StandardButton.Yes \| StandardButton.No`、既定ボタンは `StandardButton.No`)を表示する。`Yes` 以外の場合は保存せず、ダイアログを開いたままにする。カテゴリが未変更のときは表示しない。新規登録時は表示しない |
| 確認ダイアログの文言 | タイトル「管理番号の変更」。本文「カテゴリを変更すると、管理番号が新しいカテゴリのものに再採番されます。印刷済みのラベルは再印刷が必要です。保存しますか?」(固定文とし、新しい管理番号は保存前に確定しないため表示しない) |
| Repository の変更方法 | `ItemRepository.update` のシグネチャ・SQL は変更せず、`ItemRepository.set_code(item_id, code)` を追加する。`_execute(..., integrity_mappings=(_UNIQUE_VALIDATION,))` を使い、UNIQUE 違反は既存の `_UNIQUE_VALIDATION` で業務例外へ変換する |
| 版数 | アプリ版数を `0.3.1` に引き上げる(`pyproject.toml`・`uv.lock`・`README.md`)。`SCHEMA_VERSION = 5` は維持する。`README.md` の「v0.3.0 の DB・バックアップは v0.2.0 以前のアプリでは開けません」は、スキーマ版が変わらないため据え置く |

### 2.4 対象外

- 旧管理番号の履歴化・検索(旧番号での検索、読み替え表など)
- DB スキーマ・マイグレーションの変更
- 一覧の列の幅・順序・表示/非表示の保存、列の並べ替え機能
- CSV・在庫表印刷の列構成の変更(用途は含まれている)
- 既存品目の一括再採番、カテゴリ接頭辞の変更機能
- 列添字の定数化などのリファクタリング(今回は添字の直し込みのみ)
- リリース作業(タグ付け・インストーラーのビルド)。タグは `main` に含まれるコミットに付け、push 前に利用者の確認を得る
