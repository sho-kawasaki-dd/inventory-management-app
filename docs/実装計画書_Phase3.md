## 1. 目的

- 在庫操作(入庫・出庫・返品・廃棄・棚卸)を画面から記録できるようにする。
- 品目ごとの履歴を閲覧でき、誤操作を逆仕訳で取り消せるようにする。取り消せない行は操作不可とし、理由を表示する。
- 数量・単価・1 操作の金額・集計値に業務上限を設け、超過時は業務例外で処理を中断し、履歴・数量・価格・集計値をまとめてロールバックする。整数の精度を保ち、DB 内での REAL 化を防ぐ。
- 在庫操作の保存と再描画が 0.5 秒以内であることを計測で確認する(開発計画書 7.5)。
- 出庫・廃棄の費用を入庫(ロット)単価の先入先出法(FIFO)で統一的に計上し、発注主体別の費用を引き当てたロットの発注主体へ帰属させる(3c)。

### 2.4 数値上限・オーバーフロー対策

#### 2.4.1 採用する業務上限

| 対象 | 範囲・上限 |
| --- | --- |
| 品目の現在数量・初期数量・棚卸実数・閾値 | 0〜1,000,000(100 万) |
| 1 回の操作数量・推奨発注数 | 1〜1,000,000。推奨発注数は `None` 可。履歴の `delta` は -1,000,000〜1,000,000 |
| 参考価格・記録単価 | 0〜10,000,000 円(1,000 万円)、`None` 可 |
| 1 操作の金額 | 出庫・廃棄(とその取り消し行。取り消し行は元の `reason` を引き継ぐ)で `abs(delta) × unit_price` が 100,000,000 円(1 億円)以下。5.7 の支出額・廃棄額に入る種別に限定し、入庫・返品・棚卸・初期数量には適用しない。単価 `None` は算定不能として許可し、0 円とはみなさない。3c で FIFO 原価 `cost_amount` が 100,000,000 円以下という定義に置き換える(2.5.2) |
| 集計金額 | 全品目の支出額・廃棄額それぞれ 0〜1,000,000,000,000 円(1 兆円)。両指標を合算して判定しない |
| 集計数量 | 全品目の入庫数・出庫数・廃棄数それぞれ 0〜1,000,000,000,000(1 兆)。現在数量の合計とは区別する |

- 数量・金額の計算は Python の任意精度整数で行う。SQLite INTEGER は符号付き 64 ビットであり、SQL の加算・乗算は上限超過で REAL 化し得るため、型宣言だけには依存しない。
- 集計の種別・符号・帰属・期間判定は開発計画書 5.7 を維持する。取り消しは元行の期間・クライアント・発注主体に対して相殺し、返品・棚卸・初期数量は集計指標に含めない。
- 月次・年度・全期間および内訳の各合計に同じ集計上限を適用する。正しい取り消しは同じ期間・帰属で相殺され、各部分集計は非負で全期間の全品目合計以下となるため、保存時には全期間の 5 指標を検査して月次・年度・内訳も保証する。年度開始月の変更で再走査・上限変更は不要とする。

#### 2.4.2 保存・集計・例外の扱い

- 上限定数は既存の独立した契約 `core/models.py` に集約する。UI・Service・DB の制約定義で値を一致させ、`core/`・`db/` の PySide6 非依存と依存方向を維持する。DB から Service や新しい業務モジュールを参照しない。
- Service は `BEGIN IMMEDIATE` 内で最新の品目・履歴を取得し、適用単価、差分、操作後数量、1 操作の金額、操作後の集計値を検証する。品目登録・価格編集・全在庫操作・取り消しに適用し、価格編集では過去履歴の単価や集計値を変更しない。
- 全期間の 5 指標を 1 行の集計管理テーブル `total_aggregates` (単一行制約 `id INTEGER PRIMARY KEY CHECK (id = 1)`)で保持し、履歴・数量・参考価格と同じトランザクションで更新する。カラムは `inbound_quantity`・`outbound_quantity`・`disposed_quantity`・`expenditure`・`disposal_amount` とし、すべて `INTEGER NOT NULL` で `typeof(...) = 'integer'` および範囲 `0〜1,000,000,000,000` の CHECK 制約を設ける。これは履歴から再構築可能な派生値とし、履歴を正とする。通常の保存では全履歴を毎回走査せず、操作の寄与分だけを Python 整数で加減算する。新規スキーマ(`schema.sql`)でも初期行 `INSERT INTO total_aggregates (id) VALUES (1);`(各指標は既定値 0)を投入する。
- 上限超過は項目・上限が分かる `ValidationError` を送出し、コミットしない。履歴 INSERT 後など途中で失敗しても、数量・履歴・価格・集計管理テーブルをすべてロールバックする。UI は `run_guarded` で表示し、成功通知を発火せずダイアログを維持する。
- `reversal_block_reason` と `reverse` は同じ数値検証(取り消し後数量 ≤ 1,000,000)を共有し、超過時は「取り消し後の在庫数が上限(1,000,000)を超えるため実行できません」を返す。確定時に再検証する。取り消し行の単価・数量は元行のコピーで、集計値は減る方向にのみ変化するため、操作金額・集計上限の再検査は不要とする(集計値が負になる場合は履歴不整合として CHECK 制約違反で更新を失敗させる)。
- DB は数量・単価・差分・集計管理テーブルに整数型と範囲を保証する CHECK 制約を設ける。SQLite は動的型付けのため型宣言だけでは REAL や文字列を受け入れてしまうことから、整数列には `typeof(col) = 'integer'` (NULL 許可列は `typeof(col) IN ('integer', 'null')`)を適用して REAL や不正型を厳格に拒否する。
  - `items`: `quantity`(0〜1,000,000)、`reorder_threshold`(0〜1,000,000)、`reorder_quantity`(NULL または 1〜1,000,000)、`reference_price`(NULL または 0〜10,000,000 円)
  - `stock_movements`: `delta`(-1,000,000〜1,000,000)、`unit_price`(NULL または 0〜10,000,000 円)、および出庫・廃棄の 1 操作金額 `CHECK (reason NOT IN ('out','dispose') OR unit_price IS NULL OR abs(delta) * unit_price <= 100000000)`(`delta`・`unit_price` の型は各列の CHECK で保証する。3c で `cost_amount` の範囲 CHECK に置き換える。2.5.2)
  - `total_aggregates`: 全 5 指標 `0〜1,000,000,000,000`
  上限制約違反は Repository で `ValidationError` に変換する。
- ReportService は SQL 1 本で対象期間の履歴・帰属情報を取得し、Python 整数で数量・金額を集計して内訳を畳み込む。SQL の `SUM`・REAL への変換で精度を保証しない。取り消しを含む全行を集計し終えた最終値で上限を判定し、行の読込順に依存する途中合計で誤って拒否しない。
- 集計管理テーブルの初期化・再構築・検査も Python 整数を使用する。バックアップ・復元時は、全品目・全履歴(廃止・取り消し済みを含む)の上限・型・金額を検査し、履歴から再計算した 5 指標と保存済み集計値の一致を確認する。

#### 2.4.3 スキーマ変更・既存データ

- 次のスキーマ版(v3)へマイグレーションし、`schema.sql`・`migrations.py`・`SCHEMA_VERSION`・版別検査定義を同時に更新する。SQLite では `ALTER TABLE` で既存 CHECK 制約の更新やカラム変更を行えないため、`items` および `stock_movements` はテーブル再構築を行う。
- **移行機構の拡張**: 現行の `MIGRATIONS: dict[int, str]`(`executescript` のみ)では Python 整数による事前検査・集計初期化を表現できない。`dict[int, MigrationStep]` とし、`MigrationStep` は `apply: str | Callable[[sqlite3.Connection], None]`・`precheck: Callable[[sqlite3.Connection], list[str]] | None`・`rebuilds_tables: bool` を持つ。`open_database` と `prepare_restore`(現状は `core/services.py` に同じ移行ループが重複)は共通関数 `migrate_schema` を使う。`check_migration_path` の型も更新する。
- **共通の検査モジュール**: 上限・型・金額の検査と集計の再計算は新モジュール `db/integrity.py`(`find_limit_violations(conn) -> list[str]`・`compute_aggregates(conn)`。Python 整数で計算し、`core/models.py` の上限定数のみ import する)に置き、移行・復元・テストで共用する。
- **事前検査**: バックアップ作成前に全版分の `precheck` を実行する。旧 DB の全品目・全履歴(廃止・取り消し済みを含む)の型・範囲・出庫・廃棄の 1 操作金額と、全期間の集計上限を検査し、上限超過・REAL 化・不整合があれば `MigrationError`(`backup_path=None`)で中止する。メッセージに違反を最大 20 件(テーブル・ID・列・値・上限)と「データベースは変更されていません」を含める。中止時は `pre-migrate_*` バックアップを作成しない(起動のたびに不要なバックアップが増えないようにする)。自動切り詰め・丸め・履歴削除・現行データの修正はしない。リリース前のため自動修復は提供せず、開発者が `sqlite3` で該当行を修正する。
- **再構築手順と外部キー**: `PRAGMA foreign_keys` はトランザクション内では効かない。`rebuilds_tables=True` のステップは、トランザクション外で `PRAGMA foreign_keys = OFF` を実行し、`finally` で必ず ON に戻す。トランザクション内の順序は次のとおり。
  1. `items_new` 作成 → コピー → `DROP items` → `RENAME items_new TO items` → `trg_items_updated_at` 再作成
  2. `stock_movements_new` 作成(自己参照は最終名の `REFERENCES stock_movements(id)` で記述)→ コピー → `DROP stock_movements` → `RENAME` → 索引(`idx_movements_item_purchase` を含む 4 本)再作成
  3. `total_aggregates` 作成と初期行投入(`compute_aggregates` の結果)
  4. `PRAGMA foreign_key_check` が空であることを確認 → `inspect_schema` → `user_version = 3` → COMMIT
  - 既存の ID、外部キー参照、取り消し参照(`reversal_of UNIQUE`)、部分インデックス、トリガーを漏れなく保持する。列の順序は `schema.sql` と一致させる(`inspect_schema` が列定義を比較するため)。
- **スキーマ検査と RENAME の引用符**: RENAME 後は `sqlite_master.sql` が `CREATE TABLE "items" (` と引用符付きになり、`normalize_sql` が引用符付きトークンを保持するため不一致になる。`normalize_sql` で `[A-Za-z_][A-Za-z0-9_]*` に一致する二重引用符付き識別子の引用符を外して小文字化する(単引用符のリテラルは保持)。`SCHEMA_SPECS[3]` は移行 DDL ではなく `schema.sql` から生成して正本とし、`SCHEMA_SPECS[1]`・`[2]` は現状のままとする。「v2 → v3 移行後と新規作成 DB のスキーマが一致する」ことをテストで保証する。
- 集計管理テーブル `total_aggregates` の作成・初期値投入(全履歴から Python 整数で算出した 5 指標を 1 行登録)と `user_version = 3` への更新は、版の適用・検査と同一トランザクションに含める。失敗時は元のスキーマ・データ・版数を維持する。既存の移行前バックアップと復元の保全手順を維持する。
- 本書は実装計画であり、現時点で対策済みとは扱わない。実装・境界値テスト・性能計測・CI 成功をもって完了確認する。

### 2.5 FIFO 原価計上(3c)

正本は開発計画書 1.5・4.2〜4.4・5.2.2・5.3・5.7・7.2。本節は 3c の実装上の決定と範囲を定める。3a-1・3a-2・3b の完了済み記録は変更せず、3c で置き換わる項目は 2.2・2.4 に注記した。
2.4.3 の v3 スキーマ・旧方式集計の記述は 3a-1 当時の仕様として保持し、3c では以下の旧版保持・v4 変換の規約を優先する。

#### 2.5.1 決定事項

| 項目 | 決定 |
| --- | --- |
| 評価方法 | 出庫・廃棄の費用は入庫(ロット)単価の FIFO で計上する。移動平均法・後入先出法は対象外 |
| ロット | 取り消しでない `in` 行、および `adjust` かつ `delta > 0` の行(初期数量・棚卸増加)。引当順は `moved_at` 昇順、同時刻は `id` 昇順 |
| 期首在庫の単価 | 初期数量・棚卸増加は操作時点の参考価格をロット単価とする。参考価格が未登録なら単価不明ロット |
| 単価不明ロット | 入庫時に単価が空欄で参考価格も未登録の場合を含め許可する。出庫・廃棄の金額には含めず、「単価未登録数量」(引当明細から算出)に計上する |
| 費用に含める操作 | 出庫(支出額)・廃棄(廃棄額)のみ。返品・棚卸減少は FIFO でロット残数を減らすが費用に含めない |
| 発注主体の帰属 | 引当ロットの `purchaser_id`(入庫時点の品目の発注主体)。入庫時の上書き入力は対象外 |
| 減少・差分 0 行の `unit_price` | 通常操作の出庫・廃棄・返品・棚卸減少・差分 0 棚卸は NULL。原価は `cost_amount` と引当明細で表す。取り消し行は元行の単価をコピーし、ロットの取り消しを `delta < 0` だけで NULL 化しない |
| 消費済みロットの取り消し | 残数が元の数量に満たない入庫・棚卸増加・初期数量は取り消し不可とし、理由を表示する |
| 単価未登録の指標 | 「単価未登録の出庫件数」(`DashboardRow.unpriced_issue_count`、CSV 列「単価未登録件数」)を「単価未登録の出庫数量」(`unpriced_issue_quantity`、CSV 列「単価未登録数量」)へ変更する。発注主体別の内訳合計を全体と一致させるため |
| 参考価格 | 入庫単価の既定値・期首在庫の単価・見積に用いる。変更しても過去のロット単価・原価は変わらない |
| PR 間の互換性 | 3c-1 で金額上限判定を FIFO 見積へ切り替え、Service の契約変更に伴う既存 UI テストも更新する。3c-1 単独マージ時点で参考価格による不当な保存拒否をなくし、全テスト成功を維持する。見積表示・原価列・レイアウトは 3c-2 |
| OS 時計の巻き戻り | 通常操作・取り消しとも、対象品目の最新履歴時刻より前の記録時刻は保存前に `ValidationError` で拒否する。同秒は ID 順で許可する。現在時刻や既存履歴を補正しない(2.5.3) |

#### 2.5.2 スキーマ v4

- `SCHEMA_VERSION = 4`。`db/schema.sql`・`db/migrations.py`・版別検査定義を同時に更新する。現行の v3 DDL を固定し、`SCHEMA_SPECS[3]` はその固定 DDL から生成する。`SCHEMA_SPECS[1]`・`[2]` は維持し、最新版の `schema.sql` から生成するのは `[4]` のみとする。v3 → v4 移行後と新規作成 DB のスキーマ一致をテストで保証する
- 変更内容は開発計画書 4.2 の DDL に従う。`stock_movements` を再構築して `cost_amount`(出庫・廃棄行のみ NOT NULL・符号付き・範囲 −100,000,000〜100,000,000)と関連 CHECK を追加し、旧 CHECK `abs(delta) * unit_price <= 100000000` を削除する。`stock_allocations` と索引 `idx_allocations_lot`・`idx_movements_item_lot` を作成する
- 1 操作の金額上限(1 億円)の DB 最終防衛線は `cost_amount` の範囲 CHECK とする。Service が確定値の `cost_amount` を事前検証し、超過は `ValidationError`
- Repository: `AllocationRepository`(追加・品目のロット残数取得・引当明細取得)を追加する。`MovementRepository.insert` は `cost_amount` を受け取る。CHECK 違反は従来どおり Repository で `ValidationError` に変換する

#### 2.5.3 引当・保存(`InventoryService`)

- 既存の公開メソッド(`receive`・`issue`・`return_to_supplier`・`dispose`・`stocktake`・`create_item`・`reverse`)の呼び出し形式は維持する
- 減少操作(出庫・返品・廃棄・棚卸減少)は `BEGIN IMMEDIATE` 内で次の順に処理する: 最新のロット残数(残数が正のロットを引当順に取得)→ `core/fifo.py` の純関数で引当計画 → 不足は `NegativeStockError` → `cost_amount` の算出(Python 整数)→ 出庫・廃棄の 1 操作金額上限の検証 → 履歴 INSERT(`unit_price` は NULL、出庫・廃棄のみ `cost_amount` を設定)→ 引当明細 INSERT → `items.quantity` UPDATE → `total_aggregates` 更新
- 集計管理テーブルの寄与分: 出庫は出庫数 += 数量・支出額 += `cost_amount`、廃棄は廃棄数 += 数量・廃棄額 += `cost_amount`。返品・棚卸減少は寄与なし
- 入庫・棚卸増加・初期数量は引当を持たず、新たなロットとなる。ロット単価は 2.5.1 のとおり
- 棚卸の `unit_price` は通常操作の増加時のみ参考価格を適用し、減少時・差分 0 は NULL とする。取り消し行は差分の符号ではなく元行の単価をコピーする
- 参考価格の更新(入庫時の確認・品目編集)は、既存ロット・履歴・`cost_amount`・集計値を変更しない
- FIFO 見積: `InventoryService.estimate_outflow(item_id, quantity) -> FifoEstimate` を読み取り専用(`read_transaction`)で提供する。`FifoEstimate` は `cost_amount`(単価判明分の合計)と `unpriced_quantity`(単価不明ロットからの数量)を持つ。在庫不足は `NegativeStockError`。確定時は Service が最新のロットで再計算する
- 記録時刻の順序検証: 通常操作・取り消しの `BEGIN IMMEDIATE` 内で、書き込み前に記録時刻を 1 回取得し、対象品目の最新履歴時刻(取り消し行も含む)と比較する。UTC の秒精度で最新時刻より前なら `ValidationError` とし、履歴・引当・数量・参考価格・集計を変更しない。同秒は ID 順で許可し、履歴なしの初期数量登録では比較を省略する。取得した同じ時刻を履歴に保存する。時刻の比較処理は `core/timeutil.py` に集約し、Repository は最新時刻の取得、Service は判定と例外送出を担当する。未来への時刻補正・既存履歴の書き換えは行わない

#### 2.5.4 集計(`ReportService`・集計管理テーブル)

- 期間・クライアント・発注主体を絞る SQL は 1 本のまま、履歴に引当明細・引当ロットを `LEFT JOIN` で結合して取得する。発注主体は `COALESCE(lot.purchaser_id, m.purchaser_id)`、クライアントは `m.client_id`、期間は従来どおり取り消し行を元行の `moved_at` で判定する。集計は Python 整数で行う
- 指標の式は開発計画書 5.7 に従う(出庫数・廃棄数は引当数量、支出額・廃棄額は引当数量 × ロット単価、単価未登録数量は単価不明ロットの引当数量)。取り消し行の引当は負の数量で元行と相殺する。返品・棚卸の引当は指標に含めない
- 内訳軸によらず、同一の絞り込み条件の合計が一致することを維持する。1 回の出庫が複数の発注主体のロットにまたがる場合は、引当明細ごとに振り分ける
- `total_aggregates` の初期化・再構築・検査は `db/integrity.py` が引当明細とロット単価から Python 整数で再計算し、保存済みの `cost_amount` および集計値との一致を検査する
- v1〜v3 の参考価格ベースの集計・数値検査は旧版用として保持する。`compute_aggregates`・`find_limit_violations` と復元検査の呼び出しは、検査対象・移行途中の版数に応じて旧方式と FIFO 方式を明示的に切り替える。v2 → v3 は従来の集計結果を維持し、FIFO への変換は v4 ステップのみが担当する。旧版に存在しない引当テーブル・原価列を問い合わせない
- 集計上限(2.4.1)は従来どおり。取り消しは同じ期間・帰属で相殺されるため、各部分集計は非負で全期間合計以下になる

#### 2.5.5 取り消し

- 減少行(出庫・返品・廃棄・棚卸減少)の取り消し: 元の引当と同じロット集合で各数量を符号反転して追加し、ロット残数を元に戻す。再引当はしない。`cost_amount` は元行の符号反転(元行が NULL なら NULL)、`unit_price` は元行のコピー(NULL)
- ロット行(入庫・差分が正の棚卸・初期数量)の取り消し: ロット残数が元の数量と等しい場合のみ可能。満たさない場合は `ReversalNotAllowedError`。理由の固定文言は「この入庫(在庫増加)はすでに出庫・廃棄・返品・棚卸減少で消費されているため取り消せません」とする。取り消し行の `unit_price` は元行のコピー
- `reversal_block_reason` と `reverse` はこの検証と数量上限の検証(2.4.2)を共有し、確定時に再検証する。従来の「取り消し後の在庫が負になるため実行できません」は、ロット消費済みの条件に包含されて到達しないため削除する。履歴不存在・取り消し行・取り消し済み・差分 0 棚卸・廃止品目の理由は変更しない
- 取り消し行の操作金額・集計上限の再検査は不要(2.4.2 と同じ)

#### 2.5.6 UI の変更

- PR 分担: 3c-1 は StockMoveDialog の金額上限判定を `estimate_outflow` に置き換える最小変更と、Service の新契約に依存する既存 UI テストの更新を含む。3c-2 は見積原価・単価不明数量の表示、原価列、追加の UI 操作テスト、レイアウトを担当する。3c-1 の変更後に金額上限判定を参考価格ベースへ戻さない
- StockMoveDialog: 出庫・廃棄の金額プレビューを `abs(delta) × 参考価格` から `estimate_outflow` の FIFO 見積に置き換える。品目・種別・数量の変更時に呼び、見積原価と単価不明数量を表示する。見積原価が 100,000,000 円超なら OK 不活性とエラー表示。単価不明ロットのみで算定不能な場合も保存は可能(見積原価は 0 円と単価不明数量を併記)。入庫・返品・棚卸は従来どおり金額上限の対象外。見積の呼び出しも UI から Service 経由のみとする
- 履歴(`MovementTableModel`・`MovementRow`): `MovementRow` に `cost_amount` を追加する。列「単価」はロット単価(ロット行とその取り消し行のみ値あり、他は空欄)とし、その次に列「原価金額」(出庫・廃棄行のみ。取り消し行は負値。「1,234円」形式・右寄せ)を追加する。取り消し行・取り消し済み行のグレー表示は従来どおり
- HistoryDialog・ReversalDialog: 取り消し不可の理由に 2.5.5 の固定文言を表示する(ツールチップ)。他の挙動は変更しない
- 在庫一覧・ItemDialog・マスタ管理は変更しない

#### 2.5.7 移行・復元・検査

- v3 → v4 の `MigrationStep`(`rebuilds_tables=True`)は 2.4.3 の事前検査 → バックアップ → トランザクション外の FK 無効化の規約に従う。`finally` で必ず FK を ON に戻す。トランザクション内の順序は次のとおり
  1. 旧履歴を時系列再生し、引当・変換後の `unit_price`・`cost_amount` を算出する。通常操作の減少行とその取り消し行、および差分 0 棚卸の `unit_price` は NULL にする。ロット行とその取り消し行の単価は保持する
  2. 新 CHECK を持つ `stock_movements_new` に、最初から変換済みの履歴を INSERT する。ID・自己参照を保持して `DROP`・`RENAME` し、既存索引と `idx_movements_item_lot` を作成する。旧行を未変換でコピーしてから更新する手順や CHECK の一時解除は使用しない
  3. `stock_allocations` と索引を作成し、全履歴のコピー完了後に引当明細を INSERT する
  4. 引当とロット単価から `total_aggregates` を再計算し、FIFO 整合検査・`PRAGMA foreign_key_check`・`inspect_schema` に合格してから `user_version = 4` を設定して COMMIT する
- 事前検査(バックアップ作成前): 型・範囲の検証後に旧履歴だけで再生し、ロット残数不足・消費済みロットの取り消し・品目数量との不一致に加え、変換後の全出庫・廃棄行とその取り消し行の `cost_amount` の範囲(−100,000,000〜100,000,000)・最終集計値の上限を検査する。取り消し済みの元行も 1 操作金額の検査から除外しない。違反時は `MigrationError`(`backup_path=None`、違反を最大 20 件とメッセージ「データベースは変更されていません」)で中止し、履歴 ID・金額・上限を示す。旧仕様では正常でも FIFO 原価が上限を超える DB は移行不可とする。丸め・切り捨て・操作の自動分割・データ修正は行わず、`pre-migrate_*` を作成しない
- `db/integrity.py` に FIFO の再生と検査(`replay_allocations`・`find_fifo_violations`)を追加し、移行・復元・テストで共用する。再生は `(moved_at, id)` 昇順で、ロット作成・FIFO 消費・取り消しによる引当の戻し・ロット行の取り消しを適用する。移行前の再生は v1〜v3 の履歴だけで実行可能とし、存在しない `stock_allocations`・`cost_amount` に依存させない
- `SCHEMA_SPECS[1]`〜`[3]` と旧方式の検査・集計は保持し、v1・v2・v3 の各 DB から v4 への起動時移行と復元を検証する。各中間版ではその版のスキーマ・集計方式を使用し、v2 → v3 の結果を変えずに v4 で FIFO へ変換する
- バックアップ・復元の業務検査に開発計画書 7.2 の FIFO 整合検査を追加する。違反する復元元は理由付きで拒否し、現行 DB と元ファイルを変更しない。上書き後・自動復旧後の再検査にも同じ検査を適用する
- 移行前の通常操作の減少行・その取り消し行・差分 0 棚卸の `unit_price`(参考価格)は失われる。`pre-migrate_*` バックアップが保全する

#### 2.5.8 性能

- 出庫・廃棄・取り消しの保存と一覧の再描画は FIFO 引当を含めて 0.5 秒以内(品目 5,000・履歴 100,000 件。ダミーデータは 3c の引当・`cost_amount` を持つよう更新する)
- Service 単体の追加計測として、1 品目に多数のロット(例: 1,000)がある場合の出庫保存も 0.5 秒以内であることを確認する
- ReportService の年次・月次集計は引当明細の結合を含めて各 2 秒以内
- v4 移行時の事前検査・再生・初期化の時間は通常保存とは別に参考値として記録する
